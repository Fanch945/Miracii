## 1. 关机期间不涨：速率与频率

**现象**：应用关着时积温不涨（设计如此：每拍最多按 `max_tick_minutes`＝60 分钟计）。
人不是长期开着应用，所以"醒来不涨"这件事需要重新权衡。
实测台账（10-15）：contact 出现在本地 15:18 与 22:36，每次约 **7 小时**沉默；触发时 `connection` 0.3547 / 0.3609
——与设计值 7.33 小时吻合，人反馈的"0.3 出头"也对。

**要把两件事分开**：
- **速率**（connection 涨多快）：`connection_base` 0.0007/分，45 分钟后复利加速。
- **频率**（多久说一次）：由三个开口线 + 冷却 45 分 + 每日配额共同决定。

**人反馈的真实约束**：全天在线但间歇回话。每次回话 `reply_delta` 把 connection 砍 0.25（0.36 → 0.11），
等于**每次都重置那 7 小时计时**——所以"容易被打断"是这条 delta 的直接后果，不是速率问题。

**可选方案**（都还没做）：
| 方案 | 做法 | 代价 |
|---|---|---|
| A 唤醒补偿 | 新增 `wake_bonus_minutes`（默认 0）：应用启动后第一次 tick 额外推进这么多 | 小；比放大 `max_tick_minutes` 安全（后者会让**每次**长时间空闲都猛涨） |
| B 调速率 | 只动 `connection_base` | 治不了"被打断"，因为断点由 reply_delta 决定 |
| C 调回落 | 把 `reply_delta.connection` 从 −0.25 调小 | 直接改变"她多容易被安抚"，需与 3/4 一起看 |

**建议**：先加 A（可配、默认关），再拿真实台账看一周，别急着动 B/C。

## 2. 犹豫（hesitation）：要不要引入随机性

**先纠正一处理解**：现在的 hesitation **不加到 connection 上**，
它做的是**抬高 `contact` 门槛**：`contact = 0.35 × lift + 0.10 × hesitation`。
副作用是它有个硬上限——判定顺序里 `force`（0.50）在前，所以 `hesitation_lift ≥ 0.15` 之后就没有额外效果了。

**人想要的**：犹豫应当表达**不确定性**——越犹豫越可能"干出相反的动作"（该说时不说、该沉默时冒一句），
越不犹豫越有决心（无论决心说还是决心不说）。还提出：可否用 [−1,1]、从 1 往下减、以及**灵感机制**
（忽然想到好玩的事 → 决心分享；对话里情绪被扭 → 决心沉默）与未来的**叛逆值**。

**我的分析**：
1. **方向 vs 不确定度是两件事，建议拆开**：`hesitation ∈ [0,1]`（不确定度）× `resolve ∈ [−1,1]`（倾向）。
   塞进一根轴的后果是：判错时分不清是"她不够想"还是"她在摇摆"。
   ——人对 [−1,1] 的自我反问（"纯随机浮动的话取绝对值就够了"）是对的：**只是抖动就用 [0,1]**。
2. **"从 1 往下减"= resolve 的必然性增长**：等得越久，"必须说"压过"要不要说"。
   现在的实现里已有雏形（复利加速 + 强制线），显式化就是让 resolve 随时间向 ±1 漂。
3. **随机性怎么加才不毁掉可解释性**：保持**确定性内核 + 显式随机外圈**——
   期望仍由确定性的量决定；每次开口判定时按 `σ = hesitation_spread × hesitation` 抖动，
   并把**种子写进台账**（`decision_seed`）。于是"她为什么此刻开口"仍可回答、每一次都能复现。
   纯确定性的立场（我原来的）牺牲了体感；纯随机则牺牲了复盘能力——这个折中兼顾。
4. **灵感机制的正解是"事件注入通道"**：`warmth.apply_delta()` 早就写好了，**但没有任何调用方**。
   灵感 = 一次大幅 delta（`hesitation −0.6、connection +0.1`）。
   所以这条与第 4 条（骄傲不动）**是同一个前置**：把对话/监督的 delta 接上。
5. **叛逆值先别加轴**：轴越多越难校准。等 delta 通了、标注数据够了再谈。

**卡在哪**：需要人定两件事——(a) 拆不拆成 hesitation + resolve；(b) 接不接受"随机但记种子"这种折中。

## 3. 骄傲（pride）几乎不动

**数据**：人这两天三次 contact 时 `pride` 分别 0.06 / 0.06 / 0.06，`connection` 0.3547 / 0.3609。
**原因**：骄傲的防御线是 **0.35**，而她的 connection 几乎刚好压线——骄傲只能涨一两分钟（0.003/分）
就被回话打回去了。所以**不是人格不适用，是它从来没机会长起来**。

**但更根本的一条**：真正该驱动骄傲的是**对话内容**（被夸、被逗、被戳穿、被冷落），
那条路是 `apply_delta` —— **目前没有任何代码调用它**。这正好解释了人看到的
"监督里写着她有点小得意，骄傲却不动"。

**方案**：接上**对话 delta 注入**——每轮对话后用一个轻量判断把"这一轮对六轴的影响"抽出来
（被夸 → pride +；被逗 → valence/arousal +；被敷衍 → valence −），上限照参照实现
（前三轴 ±0.3，connection −0.5~+0.3），并在台账里留下这一笔。
**它是第 2 条灵感机制与第 3 条骄傲的共同前置**，建议优先。

## 4. 人格生活化与环境 API（大目标）

人提的愿景：supervisor 做她"查看世界"的接口——**时钟、书本内容、工作空间、新闻**；
未来可以再有 `environment` / `lib` / `note` 等；最终让人格**有自己的日程并能安排生活**。
同时由此诞生**人格自己的状态**（`persona_state`）：她也会"暂离"（在忙自己的事、甚至"设备不在身边"收不到消息）。

**我的判断**：方向对，且与现有架构天然契合——`supervisor` 已经是"她的世界接口"的雏形。
最小可落地的一步是**环境块**：她开口或回复时，system prompt 里附一段只读的"此刻她所处的环境"
（时间、手头的事、最近读到的东西）。**先只读、先不加写入**，避免与环境 API 的写权限一起引入复杂度。

**待研究**：环境块的字段清单、`persona_state` 的驱动源（应由"她正在做的事"决定，而不是模型猜）、
以及它与 `user_state` 的对称性。
