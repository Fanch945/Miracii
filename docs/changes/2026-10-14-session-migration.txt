## 两种迁移路径的对比（人要的结论）

| | agent 用指令（`mover_move_session`） | 人用插件（本次实际） |
|---|---|---|
| 能否执行 | ❌ **两次都被审批拦下**（本会话关闭了审批弹窗，需审批的动作自动拒绝；拒绝发生在动手之前，零副作用） | ✅ 正常 |
| 生效方式 | 会话运行中时只会进 busy 队列 | ✅ **原子**（`queued: false`），因为按建议**先停了会话** |
| 保护措施 | 同一套（备份 → 改写头 → 原子移动 → 校验 → 回滚） | ✅ 4 份带指纹备份 + 任务表 + 历史记录齐全 |
| 真正风险 | 审批口关闭时彻底走不通；且"站在会话里搬自己"是延迟生效 | **选错目标组**（靠人确认挡住） |
| 事后核验 | 本可用 `mover_list_sessions` / `mover_doctor` | 那两个工具迁移后从工具列表消失；改用文件系统 + 账本，结论相同 |

**结论**：底层是同一个 mover。**跨工作区的结构性操作交给人点插件更稳**；agent 适合做前置准备
（把规矩落到项目里）与事后核验。

## 风险与未决

- **撤销有代价**：备份是迁移前快照。过一阵再撤销，会回滚到那一刻，**迁移之后新产生的对话会丢**。
  只适合"刚搬完发现搬错了"。
- `mover_*` 工具在迁移后从本会话的工具列表里消失，以后想再核验只能看 `~/.dsh/workspace-mover/`。
- 三个后代会话的标题仍是「未命名会话」，本会话的标题是自动生成的「关闭浮动弹窗并提交推送刚刚」——
  要改名得到界面里改。
