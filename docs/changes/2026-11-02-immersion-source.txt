# 沉浸度的来源错了：学习队列不是她的活动

- 日期：2026-11-02
- 作者：DSH（DeepSeek Harness agent）
- 风险等级：**T2**（状态/持久化行为变更，需人签字）
- 关联提交：本文件所在提交
- 关联设计文档：[docs/WARMTH.txt](../WARMTH.txt)、[docs/WARMTH-NOTES.txt](../WARMTH-NOTES.txt)

## 规格与验收

- 规格：**沉浸度只能由"她真的在做什么"驱动**；记忆维护的待办不算活动。
- 验收：① 默认配置下，学习队列有积压也不会产生沉浸度；② 实验开关可显式打开（可逆）；③ 对话注入仍能抬起沉浸并自然衰减；④ 全库测试通过。

## 上下文与影响面（T2）

影响 `ambient_tick` 的沉浸度来源判定；不涉及记忆写入、不涉及人格文件。旧行为可用
`immersion_from_backlog: true` 完全恢复。

## 背景

人报：**近两天打开程序时依旧自主产生高沉浸度**，并质疑"学习队列影响待办判断"这个说法本身有问题。

查证（不是猜）：

| 证据 | 结果 |
|---|---|
| `supervisor.jsonl` 最近 51 条可解析决策 | **23 条带 `learn`**，且集中在 `daily`（每晚 2–3 条）与 `weekly`（2 条） |
| `heartbeat.py` 里 `apply_conversation` | **0 次**——supervisor 的说话不经过对话判线程，它影响沉浸的唯一路径就是队列 |
| 学习队列 | 20 条，最后写入 10-31 21:41（本地） |
| 机制 | 每晚 23:00 daily 写 2–3 条 → 队列"新鲜"两小时 → `activity_for_backlog` 判成 `reading` → 沉浸被设为 **0.6** |

所以"她晚上莫名埋头"= **记忆维护的待办被当成了她的活动**。人说这有问题——**成立**：
`learn_queue` 是"待采纳的论断"，不是"她正在做的事"，这个映射从语义上就错了。

## 改了什么

| 位置 | 改动 |
|---|---|
| `Config.immersion_from_backlog` | **新增，默认 `False`**（实验开关，可逆） |
| `ambient_tick` | 只有开关打开时才用积压档位；默认不再产生沉浸 |
| `load_config` / `effective_config` / `template` | 三处接线（结构性测试会抓漏接） |
| `tests/test_immersion_source.py` | 新增 4 项：默认忽略队列、实验可开、对话仍是唯一当前来源、配置可写 |

顺带修的三条老测试：它们测的是"实验打开时"的行为，已显式传入实验配置，避免默认值一变就红。

## 风险与未决

- **沉浸度现在只有两个来源**：对话注入（现行）与将来的环境 API。**在她有真实活动之前，沉浸度基本为 0**——这是诚实的状态，不是退化。
- 实验开关存在但**没有任何东西**会打开它；要不要保留它，等"人格生活化"落地时再定。
