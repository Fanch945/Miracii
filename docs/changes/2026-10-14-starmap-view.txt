## 背景

`docs/STARMAP.txt` 写明应用内不做星图可视化。观察用的画面单独放在应用外面，读现有 `starmap.jsonl`，不改记忆。

## 改了什么

| 文件 | 改动 |
|---|---|
| `observe/starmap/view.py` | 只读投影：按种类分扇区，越新越靠近双星；同一指纹、同一天连线 |
| `observe/starmap/index.html` | 本地页面：拖动、缩放、按种类开关、点星看星等 |
| `observe/starmap/打开星图.bat` | 从仓库根启动上面的页面 |

没有改 `app/`。聊天窗口里没有入口。

## 验证

```powershell
python -c "import importlib.util; spec=importlib.util.spec_from_file_location('view', r'observe/starmap/view.py'); m=importlib.util.module_from_spec(spec); spec.loader.exec_module(m); data=m.sky('miracii'); print(len(data['stars']), len(data['links']), sorted({s['kind'] for s in data['stars']}))"
```

结果：`33 22 ['episodic', 'impression', 'lore', 'semantic']`。

浏览器打开 `http://127.0.0.1:7811/`：标题为「miracii · 33 颗活跃星 · 2026-10-14」，四类开关都在，双星为樊辰宇 / 樊辰昊，四色星点与同日连线可见。

## 风险与未决

- 连线只有「同一段」和「同一天」。没有因果或对立，因为索引里没有这种字段。
- 无日期的设定星固定在外圈，不参与亮度，和 `docs/STARMAP.txt` 一致。
- 页面不随心跳自动刷新，重新运行脚本才会重读索引。

## 复核（DSH / 2026-10-14）

**结论：通过。** 两条建议、一条流程说明。

自己跑过的：

```powershell
.venv\Scripts\python.exe -c "...m.sky('miracii')..."
# stars 33 links 22 ['episodic', 'impression', 'lore', 'semantic']   ← 与你的数字一致
```

读代码确认对的地方：只读（全文无写盘调用，只写 HTTP 响应）；**无任何外部引用**（没有 CDN，符合本地优先）；只绑 `127.0.0.1`；只有两条固定路由、没有路径拼接，比应用自身的文件接口更保守；`starmap.project()` 直接复用了「无日期不计亮度」的判定，画面与规范一致；`same` 连线正好把 `impression` / `episodic` 那份内容重复**画了出来**——这是索引里的真事，看得见比看不见好。

1. **画面可能和数字打架。** `view.py:94` 的半径用 `age/180` 线性映射，而 `mag` 走的是四档 λ 衰减。于是一条 100 天前的高情感记忆和一条 100 天前的琐事会落在**同一个半径**上，可它们的 `mag` 差着一大截。建议半径改用已算好的 `brightness` 或 `mag`（payload 里就有），让"看起来近"和"算起来亮"是同一件事。
2. **`_bodies` 把分块逻辑抄了一遍**（`view.py:66-70` 对 `starmap.BLOCK_SPLIT` 的再实现）。它现在和 `starmap._blocks_of_file` 一致，但两边各改一次就会漂。建议在 `starmap` 里加一个 `block_bodies(persona_id)` 供外部取正文，别让观察页自己解析。
