## 背景

她主动开口时人往往不在窗口前：页面每 8 秒拉一次 `/api/inbox`，但窗口在后台或最小化时看不见。
需要一层桌面提醒，并且**不要在用户正盯着聊天窗口时打扰**。

## 验证

单元测试：

```powershell
.venv\Scripts\python.exe -m unittest discover -s tests -t .
# Ran 22 tests in 0.245s
# OK (skipped=1)      ← 跳过的是需显式开启的实弹
```

实弹（不调模型、不写数据）：

```powershell
.venv\Scripts\python.exe -m app.notify --force "验收：她主动开口时的提醒"
# {"fired": true, "toast": true}     ← 第三轮后；第三轮前为 {"fired": true, "toast": true, "popup": true}
```

焦点规则三态（B 组用另一个进程造一个标题为 `Miracii v0.0.1` 的窗口）：

```text
A 终端在前台      {"fg_pid": 3088, "same_process": false, "fg_title_is_miracii": false, "window_focused": false}
B Miracii 在前台  {"fg_pid": 1720, "same_process": false, "fg_title_is_miracii": true,  "window_focused": true}
C 窗口关闭后      {"fg_pid": 3088, "same_process": false, "fg_title_is_miracii": false, "window_focused": false}
```

B 组是关键：前台窗口属于**另一个进程**，仅凭标题就判为「人在看」→ 提醒保持静默。

点击聚焦：`focus_app()` → `true`，随后 `window_focused()` → `true`（闭环：点过之后不再打扰）。

复核期间的文件守卫：复核前后对 7 个文件取 SHA256，只有 `docs/NOTIFY.txt` 变化，
说明复核方没有碰实现代码。

## 风险与未决

- 通知与弹窗的**观感**只有人能判断；实弹只证明「发出去了」。
- 真实监督链路（sumapi 决定 `speak=true`）没有端到端跑过，机制层用打桩测试覆盖。
- Windows 通知会留在操作中心，这是系统行为，未做干预。
- 焦点判定用标题前缀 `Miracii`，别的程序若有同名前缀窗口会被误判为「人在看」——宁少勿扰。

## 复核（Cursor / grok-4.7-high，2026-10-13）

系统通知在心跳线程里同步调用 PowerShell（失败会连试两个 AppID，各等最多 15 秒），冷启动或超时会堵住唤醒和下一次 tick；浮层要等这条命令结束才出现。
浮层在守护线程里跑 tkinter `mainloop`，而 `python -m app` 的心跳与 pywebview 同进程，第二套界面循环有机会把主窗口拖垮；`_popup` 在窗口真正建出来之前就返回成功。
`notified:` 只在 `fired` 时落日志，焦点静默、开关关闭、两层都失败都没有记录；`proactive` 若抛错，台词已经入库，整条心跳线程却会退出。
通知会留在操作中心，主动说的话可能一直可见；点浮层只收起，不会把聊天窗口拉到前台。
多条同时出现时纵坐标会算出屏幕外；接线测试只核对 `heartbeat.notify` 是同一模块，调用被拆掉也仍然通过。

### 回应：逐条处理

| 复核意见 | 处理 |
|---|---|
| 同步调 PowerShell 会堵住 tick，失败还要再等一个 AppID | 采纳。改成**一次调用只用一个 AppID**（注册成功用 `Miracii`，否则直接上回退 ID），超时 15s → 8s，典型 <1s。tick 本身已有 45s×3 的 sumapi 请求，这个量级不改变原有节奏 |
| `_popup` 在窗口真正建出来之前就返回成功 | 采纳。加 `threading.Event` 就绪信号：`deiconify` + `update` 之后才置位，`_popup` 最多等 2s，返回值现在真的代表「已上屏」 |
| `proactive` 抛错会带走整条心跳线程 | 采纳。`deliver_speak` 用 try/except 包住调用，`proactive` 内部再逐层兜底（错误进 `toast_error` / `popup_error`）；日志改为无论弹没弹都写 |
| 点浮层只收起，不拉前台；通知留在操作中心 | 采纳前半。点击改成 `focus_app()` 后再收起；操作中心是 Windows 行为，不干预 |
| 多条浮层算出屏幕外；接线测试太弱 | 采纳。堆叠上限 4 条 + 纵坐标下限 80px；接线测试换成真的调 `deliver_speak`，断言 ping 带着已入库的那句话被调用，且 ping 抛错不外泄 |

全部 5 条均采纳，无分歧。

## 后续决定：浮层默认关闭（同日，人验收后）

实测下来浮层没被注意到：它和 Windows 通知挤在右下角同一块地方，弹出来就被盖住。既然通知
本身已经够显眼，就只留通知。

- `POPUP_ENABLED = False`（`app/notify.py`）。`proactive()` 不再碰浮层，连线程都不起，
  返回值里也不会出现 `popup` 字段。
- 浮层代码、点击聚焦、堆叠与越界处理、相关测试全部保留；测试用
  `mock.patch.object(notify, "POPUP_ENABLED", True)` 覆盖「开着时」的分支，这条路径不会失修。
- 想恢复：改一个常量。

## 复核追加（Cursor）：规矩本身

作者写前四节能做。会停住的是两处：这次算不算要登记、复核交给谁。两处都靠自觉。
`.cursor/rules/change-records.mdc` 第 14–15 行和 `docs/changes/README.txt` 的第 3 步把「回应：」安在复核动作上；`_TEMPLATE.txt` 和本文件都是作者用「回应：」答复。Cursor 每轮只稳定读到 mdc，会把复核写成回应，或把模板里的「（留空…）」当成对方正文不敢动——本文件已经换掉这句，和「只增不改」对不上。
`githooks/pre-commit` 不查记录。建议只拒绝一种情况：暂存区改了 `app/`、`tests/`、`requirements.txt` 或 `docs/*.txt`（不含 `docs/changes/`），却没有新增或追加 `docs/changes/*.txt`。错别字仍靠人判断。
「重名加 `-2`」在两边都还没提交时互相看不见，追加式合并没有规则。本文件同日又塞进「浮层默认关闭」，和「一次改动一条」冲突。后续另开 `YYYY-MM-DD-<短名>-followup.txt`；撞名用时刻，不要 `-2`。
mdc 把「最近一条实例」钉成这篇 notify，后来的人会照着这段复核对话写，而不是 `_TEMPLATE.txt`。SHA256 对照和「复核要附可执行命令」只在 README 的「建议」里，mdc 没有，所以上面那节复核是纯散文，作者得自己发明验证。
