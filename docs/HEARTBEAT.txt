# 后台人格终端（心跳）有没有必要

短答：要全天候、要主动找你，就要有一个不依赖网页请求的进程。说话模型本身当不了这个进程。

## 网页请求能做什么

你发一句 → 服务醒一下 → 回一句 → 睡。
这够「能聊」。不够「她还在过自己的时间」。

关浏览器之后：没有空闲计时、没有日程窗口、没有夜间压缩记忆、没有「过了两小时她想起你说过今晚有实验」。

## 心跳进程做什么（Generative Agents 的规划环，收窄版）

每隔一段真正该醒的时间才醒（STM、印象、日/周），中间进程阻塞睡眠，CPU 接近空闲：

  读时钟、quiet、quota、上次对话间隔、keeper 尾部、working 体积
  → 把这些交给监督 skill（另一个 API）
  → 监督只输出 JSON：沉默 / 开口 / 压缩 / 排队新知识 / 可选的自选任务（时长用番茄钟作参考，不是作息表）
  → 运行时执行文件操作；开口才调用说话模型

聊天到来时网页 ping 一下心跳（本机 UDP），不必靠轮询发现「5 分钟窗口被重置了」。

这就是 MemGPT 里「模型可以 request_heartbeat」的本地版：控制流在代码里，人格不在主循环里自说自话。

## 为什么不要让聊天模型 24 小时自己编排

- 它对「继续说」有先验，会刷屏
- 它看不见真实时钟，除非这轮问到时间/日历，运行时才塞【此刻】和 calendar.txt（skills/clock）
- 它会把压缩记忆当成聊天任务，口吻变助手
- 费用和延迟都会炸

监督模型更笨、更短、更常选沉默，这是优点。

## 和现在已有程序的关系

keeper：只盯文件落盘，是磁盘日志，不是人格。
uvicorn：只服务网页，没人请求就闲着。
heartbeat：才是「人格还在」的那一层。三者可以同机常开。

Windows 上就是一个保持运行的 Python 进程（本仓库 `python -m app.heartbeat`）。以后可改成系统服务。不必上服务器，本机不休眠即可。

## 主动话题的约束（没有这些就会吵）

- quiet 时段禁止
- 每天最多几句（schedule 里 quota）
- 你刚说过话则禁止抢麦
- 话题必须能在 working / 日程 / 未完成的事里找到锚，禁止空泛「在吗」
- 监督说 speak=false 时，心跳什么都不生成

## 现在做到哪

心跳循环睡到截止点再醒：对话重置 5 分钟 STM，然后 30 分钟印象，再日/周图式。见 docs/CONSOLIDATION.txt。
`python -m app.heartbeat` 不轮询。聊天 ping 叫醒；否则等到 STM / routine / 23:00。
默认不往聊天页塞消息。stm/routine 即使没有 sumapi 也会做文件级巩固。番茄钟只出现在监督提示里，当作她给自己排任务的时长参考，不锁回话。
